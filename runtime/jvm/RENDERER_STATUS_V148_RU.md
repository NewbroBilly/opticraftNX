# OptiCraft Switch v148 — состояние рендерера после host-проверки

v148 продолжает исходный проект v147 и сохраняет исходный архив без изменений.

## Изменения

- Добавлено состояние `glColorMask(ZZZZ)V` в LWJGL GL11 bridge и программный framebuffer. Маска применяется и при очистке, и при отрисовке.
- Добавлено правило верхнего/левого ребра при растеризации треугольников, чтобы общая диагональ двух треугольников не рисовалась дважды при alpha blending.
- Координаты текстуры интерполируются с учётом однородной `q`; texture matrix применяется к четырёхмерной координате.

## Проверки

- `run_software_renderer_texture_test.sh` — PASS: текстура, обе ориентации quad, alpha blending, цветовая маска.
- `run_gl_compat_core_test.sh` — PASS: состояние GL, матрицы, преобразование примитивов.
- `run_lwjgl_gl11_bridge_test.sh` — PASS.

## Повторный запуск оригинального клиента

Использованы оригинальные `minecraft.jar`, `lwjgl.jar`, `lwjgl_util.jar`, `jinput.jar` и bundled `rt.jar` из OptiCraft JAVA LITE 1.2.5.

- Зарегистрировано 1 152 класса клиента и 16 818 классов runtime-библиотек.
- Выполнено 30 000 001 bytecode-инструкций, получено 30 кадров.
- `ORIGINAL_MINECRAFT_FIRST_FRAME=PASS`.
- Кадр: 2 979 уникальных цветов, 402 811 непустых пикселей; снимок `SCREENSHOT_MAIN_MENU_HOST_v148.bmp`.
- Меню всё ещё содержит заметные диагональные артефакты в шрифте и текстурах. Метрики кадра совпали с предыдущим контрольным запуском, поэтому `glColorMask` не устранил оставшийся дефект.

Probe остановился по лимиту внутри `adz.a(DDD)V` (pc=544). В диагностике также есть `LWJGLException: Native cursors not supported` и NPE в `hu.updateChunkLoading()`. Это host-side достижение первого меню и 30 кадров, но не полный игровой цикл.

## Ограничения

Полный игровой NRO, сборка через devkitPro/libnx с подключённой JVM и проверка на физической Nintendo Switch не выполнены. Для полноценного запуска остаётся устранить графические артефакты, пройти игровой цикл за текущей границей, подключить runtime к Switch input/display и проверить сборку/запуск на устройстве.

## Продолжение диагностики — текстуры и sampling

Добавлен маршрут `GL11.glPixelStorei(II)V` к существующему backend. Повторный host probe дал тот же кадр (2 979 уникальных цветов, 402 811 непустых пикселей), значит pixel-store alignment не был причиной полос.

Исправлен расчёт координат texel для `GL_CLAMP` при линейной фильтрации: нормализованные координаты теперь переводятся как `u * size - 0.5`, с clamp соседних texel на границе. Тест проверяет центры и края 2×2 RGBA текстуры. Texture sampling, GL texture API и LWJGL bridge — PASS. Новый кадр оригинального клиента снова имеет те же метрики; видимый дефект не устранён, вероятно меню использует nearest path. Следующий шаг — записать вызовы `glTexParameteri` и фактические UV/ID текстур для проблемного GUI atlas.
## Трассировка реальных texture calls

В диагностической пересборке оригинального клиента записаны GL texture calls. Первые texture uploads — RGBA/unsigned-byte, размеры 16×16, 128×128 и 256×256; передано ровно `width × height × 4` байт, `GL_UNPACK_ALIGNMENT=4`. Клиент выставляет `GL_NEAREST` для min/mag на ранних атласах; `GL_LINEAR` встречается у других texture IDs. `glPixelStorei` в этом запуске не вызывался. Это исключает сдвиг строк из-за unpack alignment и объясняет, почему новые GL sampling правки не поменяли меню.

Следующий шаг диагностики — сопоставить GL texture IDs с Java resource names и сравнить загруженные байты/UV с GUI atlas. Текущая трасса ограничена первыми вызовами и не меняет штатную сборку.
